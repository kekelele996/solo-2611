# v4 · 01 · 需求说明

## 1. 目标与衡量方式

目标：固定时间内产出更多通过质检的数据。

| 指标 | 定义 | 现状 | v4 目标 |
|---|---|---|---|
| 会话成功率 | 被接受的会话数 ÷ 已发出题面的会话数 | 约 28%（73 ÷ 258，含未发出题面的尝试，偏低估） | ≥ 60% |
| 悬空运行数 | `state.json` 停在 `running` 且无人看管的尝试数 | 累计 79 | 0 |
| 作废的容器时间占比 | 未产出数据的容器运行时长 ÷ 全部容器运行时长 | 未统计；已知跑满时限一项约 70 小时，258 次尝试合计约 198 小时 | 上线后比基线下降一半以上 |
| 每容器小时产出 | 被接受的会话数 ÷ 容器运行总小时 | 约 0.37 条/容器小时（73 ÷ 198） | 上线后比基线提高 50% 以上 |

"现状"两项未统计的指标由 P0 阶段的基线脚本补齐（见 `03-dev-plan.md` T0.1），目标值在基线出来后复核一次。
60% 这个数字是按"限流、5xx、截断三类不再重跑"估出来的，不是实测值。

## 2. 现状诊断

### 2.1 数据来源

`~/claude-runs/solo-2611/*/monitor/state.json`，统计日期 2026-11-13，共 258 次尝试。

| 尝试状态 | 次数 |
|---|---|
| `accepted` | 73 |
| `rejected` | 93 |
| `running`（悬空） | 79 |
| `cancelled` 及其他 | 13 |

`rejected` 的 93 次按原因分：限流 429 共 32 次；回复截断、许诺下一步或向用户提问共 17 次；网关 5xx 共 8 次；
跑满时限 55 次；其余为错误文本里带"超时""中断"字样的短时失败和容器名问题。

跑满时限的 55 次中，有末条时间戳的 54 次**全部**在终止前 70 秒内仍在产生输出。
也就是说，当前 7200 秒的一刀切超时杀掉的基本都不是卡死的题，而是在正常工作的题。
这是把固定超时改为"静默计时"的直接依据（`02-design.md` §2.1、T0.4）。

### 2.2 三个根因

**根因一：等结果的脚本和模型绑在一起。**
`scripts/solo2611.py` 的 `cmd_run` 在前台循环等待容器结束。外层 Agent 的命令超时、会话关闭或工作台后端重启都会让它退出，
`state.json` 停在 `running`。再次执行 `run` 时 `_check_workspace_pristine` 发现工作区已改动而拒绝，只能 `reset` 重来。
按 Ctrl-C 时代码还会主动停容器并重置工作区。

**根因二：任何结构不完整都整题重跑。**
429、5xx、回复截断这些情况下模型已经完成了一部分甚至大部分工作，重跑等于全部丢弃，并且重跑还会再次撞上限流。

**根因三：多道题同时启动。**
2026-11-13 07:23:07 到 07:23:15 的 9 秒内启动了十多道题，这一批后来全部没有结果。
工作台有启动间隔（`dispatch.launch_spacing_seconds`），但由 Agent 直接调技能的运行不经过工作台，没有间隔。

### 2.3 为什么无头模式做不了"继续"

读取镜像 `adminfather/benzhi-claude-code2:20261110` 的 `/usr/local/bin/entrypoint.sh` 得到：

- 只接受 `interactive`、`print` 两个参数，其他参数报 `session recovery are not supported`。
- 用 `$HOME/.task-session-started` 拒绝同一容器第二次启动。
- `print` 模式执行 `claude -p`，进程退出后会话结束。

所以要在同一个会话里发第二条消息，只能用 `interactive` 模式并保持容器不退出。
改镜像入口、`docker start` 复用容器、加 `--resume` 参数都违反官方容器规范，不采用。

### 2.4 规范依据

官方标注说明的问答「截断与"继续"处理」：模型自己中断后可以人工输入"继续"；Prompt 与 PromptID 提交前一轮的；
打分和评价基于"继续"之后的轮次综合评价（可能不止一次继续）；在【其他问题】中说明中断情况。

同一份说明在正文里又写了"每一个 session 仅可进行一轮有效交互"。两处如何同时成立需要项目方确认，见 §6 Q1。

## 3. 新规则（权威表述）

| 编号 | 规则 |
|---|---|
| R1 | 一题只有一次会话机会：一个容器、一个 SessionID。不再有"恢复初始快照后重跑"。 |
| R2 | 会话成立的判定：容器内轨迹里出现了内容与 `delivery/提示词.md` 一致的真人消息。成立之前的失败叫**启动失败**，不算用掉机会，最多再启动 2 次。 |
| R3 | 一轮回复结束后，判定为"完整"就收尾；判定为"中断"就在同一会话里发"继续"。 |
| R4 | "继续"最多发 2 次。已经发过 2 次后又出现中断，终止这道题。 |
| R5 | 所有"继续"都计数，不区分中断原因，也不区分自动发还是人工发。 |
| R6 | 限流和 5xx 造成的中断，先等待再发"继续"；等待期间容器保持运行并占用名额。 |
| R7 | 鉴权失败（401）、额度用尽、模型名不匹配：不发"继续"，会话原地保留最多 30 分钟等人处理；处理好后发"继续"（计数），超时则终止。 |
| R8 | 会话总时长达到上限：终止这道题，不发"继续"。 |
| R9 | 长时间没有任何新轨迹（默认 20 分钟）：终止这道题，不发"继续"。 |
| R10 | 监督器、Agent、工作台后端断开都不算中断。重新接回不消耗任何次数。 |
| R11 | 终止是终态。被终止的题只能换题，对应工程进入冷却。 |
| R12 | 无头模式保留为回退选项，同样只有一次机会，没有"继续"能力。 |

"中断"的具体判定条件见 `02-design.md` §3.4。

### 3.1 一次会话的全部结局

| 结局 | 条件 | 数据 |
|---|---|---|
| 接受，0 次继续 | 第一轮完整 | 正常交付，备注为空 |
| 接受，1–2 次继续 | 某一轮完整，之前发过 1–2 次继续 | 交付，备注写明中断次数 |
| 终止：继续用尽 | 已发 2 次继续后仍中断 | 不交付，换题 |
| 终止：超时 | 达到总时长上限 | 不交付，换题 |
| 终止：无进展 | 超过无进展时限 | 不交付，换题 |
| 终止：等待处理超时 | R7 的 30 分钟内无人处理 | 不交付，换题 |
| 终止：人工放弃 | 人工执行 `abort` | 不交付，换题 |
| 启动失败 | 会话未成立，且启动重试用尽 | 不交付；不进冷却，可重新排队 |

## 4. 功能需求

### 4.1 技能

| 编号 | 需求 |
|---|---|
| FR-S1 | 新增受管交互模式并设为默认：脚本在后台终端里启动交互容器、发送题面、监视每一轮结束、按规则发"继续"或收尾。 |
| FR-S2 | 监督器独立于调用它的进程。调用方退出、被杀、超时，监督器和容器都不受影响。 |
| FR-S3 | `resume` 命令幂等：任何时候执行都把这道题带回"有人看管"的状态，并返回当前进度。 |
| FR-S4 | `run-status --json` 返回机器可读的进度：第几轮、已继续几次、最近活动时间、下一步该做什么。 |
| FR-S5 | 每一次判定和动作都追加写入事件日志；状态文件原子写入并加锁。 |
| FR-S6 | 轨迹校验改为：真人消息 = 1 条题面 + N 条"继续"（N ≤ 2），其余条件不变。 |
| FR-S7 | 有"继续"时，交付表「备注」和平台 `other_issues` 写入固定句式；与明文 Key 备注并存时用分号连接。 |
| FR-S8 | 评分校准增加规则：因模型自身原因中断（截断、许诺下一步、提问）过的题不得评 5 分。 |
| FR-S9 | 轨迹时间线标出每次中断与"继续"的位置和原因。 |
| FR-S10 | 技能层的启动间隔：两次容器启动之间至少间隔 `claude.launchSpacingSeconds`，不依赖工作台。 |
| FR-S11 | 批量入口 `resume-all`：列出指定目录下所有未结束的题并逐一接回。 |
| FR-S12 | `SKILL.md` 增加"收到'继续'时怎么做"一节，Agent 据此从断点接着做而不是重新开始。 |
| FR-S13 | 历史悬空尝试清理：`doctor --fix-stale` 把无人看管且容器已不存在的 `running` 尝试标为 `lost`。 |
| FR-S14 | 回退开关 `claude.runMode = print`，切回无头模式。 |

### 4.2 工作台

| 编号 | 需求 |
|---|---|
| FR-W1 | 运行执行器改为"启动后脱离"：发起运行后立即返回，之后靠轮询 `run-status` 和读事件日志跟踪。 |
| FR-W2 | 后端重启后认领在跑的会话：读状态即可，不重新启动、不终止。 |
| FR-W3 | 运行阶段的计费重试上限改为 0；启动失败独立计数，上限 2。 |
| FR-W4 | 新失败类别与处置：继续用尽、超时、无进展、等待处理超时 → 隔离并换题、工程冷却。 |
| FR-W5 | 会话内的限流、5xx 不再作为任务失败上报，改为会话事件；仍然驱动弹性下调和网关探测。 |
| FR-W6 | 数据库记录每一轮、每一次中断和"继续"；吞吐统计增加继续率、终止率、每容器小时产出。 |
| FR-W7 | 接口新增：接回、人工发"继续"、放弃、查询轮次。 |
| FR-W8 | 任务页显示"第几轮、已继续 x/2、最近一次中断原因、下次动作倒计时"；调度页显示继续率与终止原因分布。 |
| FR-W9 | 设置项：继续上限（0–2）、运行模式、等待处理时限；移除"尝试次数"。 |
| FR-W10 | 无进展守护、运行超时守护认识"等待后继续"状态，不误判。 |
| FR-W11 | 等待中的容器继续占用名额；容量页如实显示"运行中 n，等待继续 m"。 |
| FR-W12 | 被终止的题自动归还领取并触发补位。 |

### 4.3 非功能需求

| 编号 | 需求 |
|---|---|
| NFR-1 | 监督器崩溃后 60 秒内可被 `resume` 接回，不丢会话。 |
| NFR-2 | 同一道题任何时刻最多一个监督器。 |
| NFR-3 | 状态文件在任意时刻被杀进程后仍是合法 JSON。 |
| NFR-4 | 4 道题同时运行时，监督器总 CPU 占用低于单核 5%。 |
| NFR-5 | 不新增第三方依赖。tmux 已在本机（3.6a），作为必需的系统依赖写入预检。 |
| NFR-6 | 升级过程不影响正在跑的会话：旧会话按旧规则跑完，新规则只对升级后启动的会话生效。 |

## 6. 待决策项

| 编号 | 问题 | 文档默认 | 影响 |
|---|---|---|---|
| Q1 | 带"继续"的数据本期是否照常收？备注句式有无要求？ | 收；句式见 `02-design.md` §4.3 | 不确认就全量上线，可能成批打回。建议先交 3–5 条试水 |
| Q2 | 启动失败（会话未成立）是否算用掉机会？ | 不算，最多再启动 2 次 | 算的话 Docker 抖动会直接废题 |
| Q3 | 跑满时限怎么办？ | 终止 | 也可选"到时限后等当前一轮结束再判"，代价是容器占用更久 |
| Q4 | 无进展怎么办？ | 终止 | 也可选"按 Esc 打断后发继续"，但轨迹里会多一条人工打断记录 |
| Q5 | 因限流、5xx 发的"继续"是否计数？ | 计数（R5） | 不计的话规则更宽，但与"超过 2 次就终止"的字面要求不一致 |
| Q6 | 中断过的题评分是否封顶？ | 模型自身原因中断的不得评 5；限流和 5xx 不影响 | 规范示例把"需人工继续"当作效率扣分点 |
| Q7 | 总时长上限取多少？ | 沿用现配置 10800 秒 | 55 次跑到时限的题里最长跑了 15409 秒；上限抬到 3 小时会更贴合实际，但容器占用更久 |
| Q8 | 终止的题是否保留现场供人工查看？ | 保留轨迹和事件日志，容器删除，工作区不重置 | 占磁盘，由现有清理策略回收 |

**2026-11-13 实现结论**：Q2、Q3 已按文档默认值实现；Q1 的备注句式与评分封顶也已实现，
但平台是否接受带“继续”的轨迹仍需 P3 的 3–5 条真实试水后才能确认。试水完成前不得把 Q1
标记为“平台已确认”。

## 7. 非目标

- 不改官方镜像，不绕过入口限制。
- 不做多轮对话数据；"继续"之外不发任何内容。
- 不让工作台代写 Feedback、代打分（沿用 v1 规矩）。
- 不处理提交平台侧的质检规则变化。
- 不在本期合并 `~/.codex/skills/solo-2611` 与 `~/.claude/skills/solo-2611` 两份副本，只要求发布脚本同时更新两处。
