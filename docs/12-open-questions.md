## 一、阻塞项（开工前必须定）

### Q1 · 工程台认证：Cookie 还是管理员令牌？【阻塞 M2】

现状：`/open/v1/*` 的 Bearer 成员令牌只读；领取必须 `POST /api/v1/...` 且需 Cookie + `X-CSRF-Token`。

| 方案 | 优点 | 缺点 |
|---|---|---|
| A. 用户名密码登录，控制台管 Cookie | 符合成员权限模型 | Cookie 会过期，作业中途需重登 |
| B. 用管理员令牌直接调写接口 | 不会过期 | 权限过大；令牌泄露风险；可能违反流程 |
| C. 把领取改为人工在浏览器点，控制台只读 | 最简单、最安全 | 破坏「全流程在控制台内」的目标 |

**建议 A**，并把「Cookie 失效」当成一等事件（顶部红条 + 一键重登 + 重登后可续做）。
**需要你确认：本地 8088 的账号是普通成员还是管理员？以及是否允许控制台保存密码到 Keychain。**

---

### Q2 · 技能路径与调用方式【阻塞 M1】

现状：技能在 `~/.codex/skills/solo-2611/scripts/solo2611.py`，同时通过 `~/.claude/skills/solo-2611` 软链。

需确认：
1. 控制台是否只支持这一处路径，还是要可配置多个技能版本（多期并存）？
2. 是否接受用**当前 shell 的 `python3`** 执行脚本（本机 Python 版本固定的前提下），
   还是要求用技能自带的 venv？

**建议**：路径可配置（默认自动探测两处软链），执行用 `python3 -I`（隔离模式，避免工作目录污染）。
不接受多版本并存（首版）。

但 `init` 需要显式传 `--tasks-dir`，请确认技能支持该参数（若不支持则退化到在 `~/claude-runs/solo-2611` 下建）。

## 二、影响体验但不阻塞

### Q4 · 是否允许「外部 Agent 写文件」这条路径长期存在

`01` 里定了：Agent 可以在控制台打开的目录里起草题面与 Feedback 草稿。
这意味着两种并存的工作方式：

- **A. 控制台内写**（人直接在编辑器里打字）
- **B. 外部 Agent 写**（Codex/Claude 在终端里改 `drafts/` 与 `delivery/feedback.md`）

需要定的：
1. 外部 Agent 直接改 `delivery/feedback.md` 时，控制台是否要在文件变化时**自动跑 `feedback --check`**？
   （建议：是，且把结果显示在界面，但不能自动改写正文）
2. 两者同时改同一文件时，谁赢？（建议：以最后写入为准，但界面提示「文件在外部被修改，已重新载入」）

### Q5 · 录屏的窗口选择是否需要「记忆 + 推荐」

同一工程反复录屏时，窗口 ID 每次可能变化。是否要做「按应用名 + 标题模糊匹配，自动高亮推荐上次的窗口」？
（建议：做，省一次鼠标点击；但不自动选中，避免录错窗口。）

### Q6 · 是否需要多期并存（26.11 之后还有 27.x）

技能目前 `period = "26.11 领域专项"`，控制台 UI 里的领域、子方向、任务类型枚举都来自技能。
若下期枚举变化：
- **A. 完全跟随技能**（推荐）：启动时读 `spec.py` 的枚举，UI 动态生成
- **B. 控制台固化枚举**：需要每期改代码

选 A 的话，本期就要保证所有枚举来自 `import spec`，不从硬编码读取（已在 T3/T4 中体现）。

### Q7 · 是否需要导出「今日工作报告」给 TPM

FR-OPS-06 是 MAY。若要，格式与字段需要定。**建议先不做**，等试跑期看真实需求。

### Q8 · 批量能力的边界是否够用

当前只允许对 `ready` 批量排队、批量检查门禁、批量导出、批量归档。
你在实际作业中是否会需要「批量领取 N 个工程」（一次领 5 个慢慢做）？
（建议：不需要 —— 领取有超时回收，屯着不用等于占坑。）

> v2 修订：允许按目标数量自动领取，但采用补位式调度，在手上限默认等于起草并发加容器并发，见 `docs/v2/02-design.md` ADR-009。

## 三、技术细节待确认

### Q9 · 工程台 ZIP 大小与解包策略

需要知道典型工程 ZIP 大小（本机样例约多少 MB？）。若单个 > 500MB，
需要把暂存区放到外置盘，并在 `config.toml` 提供 `stagingDir`。

### Q10 · GitHub 仓库策略

技能里 `github.accessTokens` + `autoPush`。已核对实现：

1. **每个任务建独立仓库**（`repo` 自动建，仓库名 = slug + 4 位随机后缀）。
2. **默认公开** —— `repo --private` 才私有，帮助文本写明「规范要求评测团队可访问，默认公开」。
3. `autoPush: true` 时，`run` 接受会话后会自动推送产物快照。

需要确认的只剩一条：**是否接受公开仓库？** 若你的 GitHub 账号下不允许公开，
需要显式给 `repo` 加 `--private`，但这可能违反「评测团队可访问」的要求，需与 TPM 确认。

**建议**：保持默认公开（技能作者已按规范设定），控制台不擅自加 `--private`。

### Q11 · 磁盘预算

一题约占用：workspace（含 node_modules 可能 500MB–2GB）+ 录屏（720p 90s 约 20–60MB）+ 轨迹（小）。
4 题并行 + 历史堆积，一个月可能 200GB+。

需确认：本机可用磁盘有多少？是否接受「导出后自动删 workspace 仅留 SHA 与 diff」？
（`04` §6 已按此设计，但默认是手动触发，可改为自动。）

### Q12 · 是否需要在 Linux/CI 上跑

NFR-08 要求除录屏外可在 Linux 运行。这会限制：
- 不能用 macOS 专有 API（本来也没有）
- 路径、权限、`fcntl` 都可移植

需要确认：CI 环境是否具备？若没有，此条降级为 SHOULD，不做 CI。

## 五、实现期补充记录（2026-11-11）

### Q13 · Feedback/录屏计划“只由技能写”与编辑 API 的契约冲突

`PROMPT.md` 的硬规矩要求 `delivery/feedback.md` 等文件只由技能写；但 `11-api-contract.md`
要求控制台 PUT Feedback 正文、保存用户编辑后的录屏计划，而技能当前没有对应的 import/save 子命令。

本期实现按更具体的 API 契约执行：显式用户输入原样落盘，不补字、不润色、不规范化；Feedback 模板、
检查结果、Excel、`state.json` 仍全部由技能产生。建议下一版技能增加 `feedback --save --file`
和 `record plan --file`，届时控制台可完全移除这两处直接写入。
