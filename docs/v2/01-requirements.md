# v2 · 01 · 需求说明书

## 1. v1 现状基线

v2 的起点不是 v1 文档，而是 v1 文档 + 实现期追加的三项能力：

| 能力 | 位置 | 说明 |
|---|---|---|
| 自动交付（autopilot） | `pipeline/autopilot.py`、`api/autopilot.py`、`AutopilotPanel.tsx` | 由 Codex Agent 无头起草题面与 Feedback，平台调度运行、录屏、检查、确认、导出；确认标注 `ackedBy: "autopilot"` |
| 无人值守录屏 | 技能 `record auto`（本地 0.2.3） | 仅 Terminal 题；离屏构建、开干净终端、逐条敲命令、隐私门禁、关窗 |
| 清理任务 | `api/purge.py`、`PurgeModal.tsx` | 预览 → 移入 `~/solo-auto/trash/` 或永久删除；进行中任务拦截 |

实测与使用中暴露的缺口（v2 的需求全部从这张表来）：

| # | 缺口 | 影响 |
|---|---|---|
| G1 | 自动交付的 Agent 命令、超时（3600s）、阶段重试（2）、并发（起草 2 / 交付 1）是代码常量 | 换模型、调并发都要改代码重启 |
| G2 | Agent 日志只能点开弹窗看尾部，无实时流、无耗时与用量统计 | 卡住时不知道在干什么，事后算不出单题成本 |
| G3 | 失败后只有「重新加入」，不能从某阶段续跑；失败原因只有一行文本 | 运行 40 分钟后在交付阶段失败，重来代价大 |
| G4 | 停止自动交付只杀 Agent，不中断已在跑的容器 | 「停止」之后仍在消耗额度 |
| G5 | 自动确认的题与人工复核的题在导出时无区别，没有抽检环节 | 质量风险最大的一项：数据不允许返修 |
| G6 | 领取、建题仍需逐题手点 | 自动交付只省了后半段 |
| G7 | `record auto` 不支持 Web 题 | Web 题只能半自动 |
| G8 | 回收站无界面、无保留期；设置页「清理预演」没有执行入口 | 磁盘只涨不降 |
| G9 | 对账不会移除目录已消失的任务行；旧版技能（0.1.x）遗留题与新题混排 | 列表里有「永远卡住」的任务 |
| G10 | 前端新、后端旧时，点按钮只得到接口不存在的报错 | 用户无法自行判断是「要重启」 |
| G11 | 后端靠终端里的 `make dev` 活着，没有常驻与重启入口 | 关终端即停 |
| G12 | 「今日导出」统计口径与导出页不一致；导出表里的录屏等是本机绝对路径 | 报数对不上；提交前要手工处理路径 |
| G13 | 旧录屏、`record import`、Chrome 内容没有隐私检查 | 可能把无关窗口内容交出去 |
| G14 | `make check` 的契约检查依赖 git 暂存状态；mypy 仅覆盖四个子包；前端包 >500kB；技能 0.2.3 未发布 | 工程债 |
| G15 | 完成/失败没有系统级通知，要回到页面才知道 | 无人值守时发现问题晚 |
| G16 | 不知道每个项目/工程被用了几次、其中交付了几次；清理任务后连领取记录与任务的关联也断了 | 选题时无法避开已做过或反复失败的工程，也无法按项目报数 |

## 2. 目标

1. **无人值守可托付**：下达「今天交付 N 题」后，可以离开机器；回来时能在一屏内看清
   成功几题、失败几题、各自卡在哪、花了多久。
2. **没人看过的数据不裸奔出表**：自动交付的题默认先进抽检队列，批次通过体检后才生成提交表。
3. **失败代价可控**：任何阶段失败都能从该阶段续跑；连续失败自动熔断，不烧额度。
4. **磁盘与列表可持续**：一个月连续作业后，磁盘占用与任务列表都不需要人工清理。
5. **平台状态自解释**：版本不一致、需要重启、设置是否生效，界面直接说明。

## 3. 与 v1 的冲突点（以 v2 为准）

| v1 条目 | v1 说法 | v2 修订 |
|---|---|---|
| ADR-004、`08` §3.3、`12` §四「全自动无人值守跑批：不做」 | 不做一键全自动 | **已按用户明确要求实现并保留**。代价（质量交给 Agent）用抽检队列与熔断来对冲，见 ADR-006 |
| `12` Q8「批量领取：不需要」 | 领取有超时回收，不屯 | 允许「按目标数量自动领取」，但受在手上限约束（FR-INT-02），本质仍是不屯 |
| FR-FBC-04「谁复核了」 | 一个必填勾选 | 拆为两条记录：**确认**（`ackedBy`：user / autopilot）与**抽检**（`audit`：仅人工） |
| FR-EXP-03「11 项完成度检查」 | 缺项不导出 | 实现已改为前 10 项通过即可（第 11 项是 Excel 本身），文档同步 |
| 五条硬规矩 | 平台不生成、不打分、不写技能目录、不硬编码表头、不强制通过 | **全部不变**。v2 新增三条，见 README |

## 4. 非目标

| 不做 | 原因 |
|---|---|
| 平台自己调用大模型写题面/Feedback/打分 | 硬规矩 1；起草永远由外部 Agent 在任务目录内完成 |
| 抽检时在平台里改 Feedback 或改分 | 改了就成了平台代写；打回后由 Agent 或人重做 |
| 多机分布式、多用户协作 | 仍是单机单用户 |
| 自动删除 GitHub 远端仓库 | 提交表引用了 permalink，删了即证据失效；只提供手动、逐个确认的入口（MAY） |
| 自研录屏、自研容器链路 | 同 v1 |
| 图表库 | 质量看板继续自绘 SVG |

## 5. 功能需求

### 5.8 使用统计（STAT）

口径定义（三个数逐级收窄，全部按「题源项目」与「工程」两级统计）：

| 名称 | 定义 |
|---|---|
| **使用次数** | 该项目/工程被领取并建成任务的次数（领取后未建题就归还的不算，单列为「领取未用」） |
| **交付次数** | 使用后任务走到单题导出完成（11 步完成）的次数 |
| **提交次数** | 交付后进入过提交批次的次数（同一任务进多个批次只算 1 次） |

| 编号 | 需求 | 级别 |

| FR-STAT-04 | 领取确认弹窗里提示该工程的历史：「已使用 2 次，交付 1 次，上次失败原因：运行结构不完整」 | P0 |
| FR-STAT-05 | 生产计划的排除规则（FR-INT-06）基于该台账：可配「排除已交付过的工程」「排除已使用 ≥ N 次的工程」 | P1 |

## 6. 非功能需求

| 编号 | 类别 | 要求 |
|---|---|---|
| NFR-V2-01 | 可靠性 | 自动交付与生产计划的状态重启后 10 秒内恢复；重启不得导致重复领取或重复拉起同一阶段 |
| NFR-V2-02 | 安全 | Agent 日志落盘与推送前做 Key 脱敏；Webhook 不发送题面、路径、SessionID；launchd 服务只绑 127.0.0.1 |
| NFR-V2-03 | 性能 | 生产线视图 60 题规模下 SSE 更新不卡顿；日志流单题每秒推送合并为 ≤ 4 帧 |
| NFR-V2-04 | 可观测 | 每题可回答：各阶段耗时、重试次数、失败类别、是否抽检及结论 |
| NFR-V2-05 | 可回退 | 所有新调度能力有总开关，关闭后行为回到 v1 |
| NFR-V2-06 | 可测试 | Agent 以假可执行文件替身测试；生产计划以 MockTransport 题源测试；新增能力后端覆盖率不低于 v1 同类模块 |

## 7. 成功判据

- 下达「今天 20 题」后无人操作，≥ 80% 的题走到「待抽检」或「完成」；其余每一题都有明确的失败类别。
- 抽检单题 ≤ 90 秒，20 题抽 30% 的总耗时 ≤ 10 分钟。
- 进入提交批次的数据，SessionID/PromptID 重复为 0，表内引用文件缺失为 0。
- 任一失败任务从失败阶段续跑，不需要重新运行容器（除非失败发生在运行阶段本身）。
- 连续作业 30 天，无需人工清理磁盘与任务列表。
- 「页面报了看不懂的错，其实只是没重启」这类情况为 0。
