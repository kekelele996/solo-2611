## 一页摘要

v2 把「自动交付」做成了可配置、可续跑、可熔断的流水线，但**调度本身不是一等公民**：

- 并发相关的 6 个参数散在设置页的三个面板里（「执行」「自动交付」「抽检与生产计划」），生产线页上只有
  预检 / 暂停 / 继续 / 停止 / 下达计划五个按钮，改一次并发要离开现场去设置页。
- 调度逻辑分在三个互不相识的循环里（`RunScheduler`、`Autopilot`、`IntakeService`），各有各的暂停与状态文件，
  「为什么现在没在跑」没有一个地方能回答。
- 异常处置只有一种：**熔断并等人**。Docker 抖一下、网关断几分钟、题源暂时没有候选，都会把整条线停到人回来点「恢复」为止。

参考项目的调度恰好相反：队列页就是控制台，容器上限、弹性扩容、启动间隔、兜底策略、断连自动启停都在队列旁边，
开着页面就能调；绝大多数故障自己停、自己测、自己恢复。

v3 的目标就是把这套能力按 solo-2611「一题一容器、单轮 pointwise」的实际形态重做一遍，并再往前走一步：

| 线 | 一句话 | 里程碑 |
|---|---|---|
| A 调度中心 | 新的「调度」页取代「生产线」成为主工作面：开关、并发、容器上限、弹性、间隔、目标都在队列旁边，保存即生效 | M11 M15 |
| B 统一调度内核 | 一个 `Dispatcher`、一条准入门禁链、一份落盘队列；每个没启动的任务都带着「在等什么」 | M11 |
| C 挂起与自愈 | 用「挂起（Hold）」取代一刀切熔断：谁挂起谁负责探测恢复，人工暂停永远不被自动解除 | M12 |
| D 异常消化 | 90 种异常情形逐条给出 检测信号 → 分级 → 自动处置 → 恢复条件 → 升级路径 | M12 M13 |
| E 兜底与看门狗 | 无进展 / 超时 / 残留进程 / 孤儿容器守护；后台循环心跳；崩溃循环识别；睡眠唤醒校正 | M13 |
| F 弹性与补位 | 按 429 实际耽误时间伸缩容器上限；在手上限按实测阶段耗时自适应；多项目加权持续补位 + 背压 | M14 |
| G 可观测 | 吞吐与阶段耗时、调度日志页、一句话解释器、故障注入与长稳演练 | M15 M16 |

预计 **约 19 个工作日**。M11 + M12 是最小可上线集合（约 10 天），做完这两个里程碑已经解决
「设置不在现场」和「一出事就停到人来」两个主要问题。

## 沿用与新增的硬规矩

v1 五条、v2 三条**全部继续有效**（平台不生成 / 不润色 Feedback、不打分、不写技能目录、不硬编码表头、不强制通过；
自动确认如实标 `ackedBy=autopilot`；抽检只读；自动领取必须有上限与熔断）。v3 再加四条：

9. **人工暂停永远不被自动解除。** 自动恢复只能解除自动机制自己挂上去的挂起，且每条挂起都记录是谁挂的。
10. **自动处置不得绕过门禁。** 任何重试、续跑、回收都只能让任务回到「由磁盘事实重新推导」的入口，
    不允许直接改写 `state.json` 的状态字段来「推进」一道题（唯一例外：把确认已死的 `running` 尝试经技能 `collect` 收尾）。
11. **破坏性自动动作必须窄。** 自动删容器 / 终止进程 / 归还领取，前提必须同时满足「平台持有该对象的归属记录」
    与「对象自身也处于可回收状态」，任何一条不满足就只告警不动手；默认守护模式是「仅观察」。
12. **每一次自动决定都要留痕且可解释。** 启动、等待、挂起、恢复、重试、放弃、回收，都写结构化事件；
    界面上任何「没在跑」的状态都必须有一句人话的原因。
