# v3 · 03 · 异常情形目录与自动处置

本文是 v3 的核心交付之一：把「能消化多种异常」落成一张可逐条实现、逐条验收的表。
每一条都对应 `05-acceptance.md` 中同编号的故障注入用例。

## 1. 处置分级与原则

| 级别 | 名称 | 含义 | 是否打扰人 |
|---|---|---|---|
| L0 | 自愈 | 就地重试 / 等待 / 纠正，队列不受影响 | 否，只记日志 |
| L1 | 单题隔离 | 这道题退出流水线（退避、隔离或作废），其它题照常；按需补位 | 否；隔离题出现在「需处理」，不发通知 |
| L2 | 局部挂起 | 某一范围停止启动新阶段（领取 / 容器 / 会话 / 录屏 / 提交），其余范围继续；自动探测恢复 | 超过最长自愈时间才通知 |
| L3 | 全局挂起（可自愈） | 不启动任何新阶段；自动探测恢复 | 同上 |
| L4 | 需要人 | 没有可靠的自动恢复信号；挂起并立即通知、进收件箱 | 是 |

处置原则（按优先级）：

1. **先保不超发、不重复副作用**，再谈恢复速度。拿不准就不启动。
2. **范围尽量小**：能隔离一道题就不挂起一个池，能挂起一个池就不挂起全局。
3. **归因失败不罚题目**：基础设施造成的失败不消耗题目的重试次数（但受单题总尝试上限约束）。
4. **恢复后不齐射**：解除挂起后重新排队的题带 0–60 秒随机延迟，并照常受启动间隔约束。
5. **同一状况只说一次**：进入记一条事件、解除记一条，中间不刷屏；同一挂起只通知一次。
6. **破坏性动作要双重确认**：平台有归属记录 **且** 对象自身处于可回收状态，才允许自动清理（硬规矩 11）。
7. **分类不出来就保守**：按 `unknown` 处理——计次数、重试 1 次、仍失败则隔离；`unknown` 扎堆则挂起领取并叫人。

## 2. 失败分类器

### 2.1 证据与优先级

分类器输入一个 `Evidence` 对象，由阶段执行器在阶段结束时组装：

```
stage            哪个阶段
exit_code        技能 / Agent 进程退出码
skill_json       技能 stdout 的结构化结果（ok / errors / code …）
skill_stderr     尾部 4 KB
container        {exit_code, oom_killed, started, finished}   ← docker inspect，可能为空
trace_tail       轨迹最后若干条事件的类型与错误字段
gate_errors      门禁返回的 errors 原文列表
agent_verdict    AUTOPILOT: DONE | FAILED <原因>
rollout_terminal ChatGPT 会话终止类型
terminated_by    guard:<名称> | user | restart | none
context          当时的挂起表、最近探测结果、是否处于睡眠唤醒后 60 秒内
```

判定顺序，命中即停：

1. `terminated_by`：被用户中断 → `control.interrupted`；被后端重启打断 → `control.restart`；被守护终止 → 对应的 `guard.*`。
2. **上下文归因**：阶段结束时刻存在相关范围的挂起，或结束前 120 秒内对应探测失败 → 归到该来源的类别
   （例如运行失败时网关探测也失败 → `gateway.unreachable`）。
3. 结构化信号：技能 JSON 的错误码、容器 `OOMKilled`、容器退出码、HTTP 状态码字段。
4. `patterns.toml` 特征表（正则匹配 stderr / 轨迹错误文本 / Agent 结论）。
5. 阶段兜底：运行阶段结束但会话结构不完整 → `run.incomplete`；Agent 自报失败 → `agent.reported`。
6. 以上都不中 → `unknown.<stage>`。

每次分类结果都带 `matched_by`（命中的是哪一步、哪条规则），写进事件，界面在隔离卡片上原样展示。

### 2.2 特征表（`~/solo-auto/dispatch/patterns.toml`）

```toml
# 新增一种已知失败只需要加一条，不改代码。顺序即优先级。
[[pattern]]
kind    = "gateway.rate_limited"
where   = ["skill_stderr", "trace_tail"]
regex   = '''(?i)\b429\b|rate.?limit|max_parallel_requests'''

[[pattern]]
kind    = "gateway.auth"
where   = ["skill_stderr", "trace_tail"]
regex   = '''(?i)\b401\b|\b403\b|invalid.?api.?key|authentication|鉴权'''

[[pattern]]
kind    = "gateway.quota"
where   = ["skill_stderr", "trace_tail"]
regex   = '''(?i)insufficient.?(quota|balance)|额度(不足|用尽)|\b402\b'''

[[pattern]]
kind    = "container.image"
where   = ["skill_stderr"]
regex   = '''(?i)pull access denied|manifest unknown|no such image|error pulling'''
# … 其余见包内默认文件
```

启动时校验：正则可编译、`kind` 在权威枚举内；校验失败的条目跳过并告警，不影响启动。
文件热加载（修改时间变化即重读）。

## 3. 重试与退避

```
下次可启动时间 not_before = now + backoff[min(n, len-1)] × 倍率 × (1 ± jitter)
  n = 该题该阶段已计费的失败次数（从 0 起）
```

- 退避期间该题状态为 `backoff`，不占任何池的名额，不参与队首选择，位置保留。
- 「立即重试」把 `not_before` 清空，不改次数。
- 续跑入口永远是 v2 的 `_advance`：重试不是「再执行一遍上次的命令」，而是「清掉该阶段的失败标记，让磁盘事实重新决定下一步」。
  因此运行阶段成功之后的任何失败都不会重新起容器。
- 止损规则（任一命中即不再重试）：
  1. 门禁 errors 指纹（规范化后取哈希）与上一次相同；
  2. Agent 自报失败的原因文本与上一次相同；
  3. 同一阶段连续两次在启动后 60 秒内失败（明显是确定性问题）；
  4. 总尝试达到上限。

## 4. 异常情形目录

列说明：**信号** = 怎么发现；**级** = §1 的级别；**处置** = 自动做什么；**恢复** = 什么时候算好了、之后做什么；
**升级** = 什么时候才需要人。编号用于验收对照。

### A. 主机与基础设施

| # | 情形 | 信号 | 级 | 处置 | 恢复 | 升级 |
|---|---|---|---|---|---|---|
| A1 | Docker daemon 停了 / 重启中 | `docker ps` 连续 3 次失败 | L2 | `docker_guard` 挂起 containers、recording；在跑的运行按 A2 / C 系列各自处理 | 连续 2 次成功 → 解除 → 清理残留 → 重新排队（不计次数） | 15 分钟 |
| A2 | Docker 响应慢（负载高） | `docker ps` 超过超时但未连续 3 次 | L0 | 本拍事实标「未知」，不启动；展示用旧快照并标注；同一时间只跑一个 `docker ps`，失败结果缓存 5 秒 | 下一次成功即恢复 | 不升级；持续则转 A1 |
| A3 | `docker ps -a` 被单个损坏容器拖垮 | 命令失败且 stderr 含容器层错误 | L0 | 退回只列运行中容器的 `docker ps`（调度本来只数运行中的）；记 `probe.docker_degraded` 一次 | 自动 | 不升级；进诊断信息 |
| A4 | 磁盘低于下限 | 剩余 < `floor_gb` | L2 | `disk_guard` 挂起 containers、intake；立刻触发一次紧急瘦身（已导出任务的依赖目录、已退出的容器、过期回收站） | ≥ 下限 × 1.2 → 解除 | 30 分钟仍不足 |
| A5 | 磁盘进入紧急档 | 剩余 < `emergency_gb` | L3 | 全局挂起；中断**最晚启动**的一个运行并清理其容器以保住其余（唯一会主动中断在跑阶段的自动动作，受守护模式约束：仅观察时只告警） | 同 A4 | 立即 |
| A6 | 写文件失败（磁盘满 / 权限） | 落盘抛 `OSError` | L3 | 状态保留在内存；全局挂起；每 30 秒重试落盘 | 写入成功 → 解除 | 立即 |
| A7 | Mac 睡眠后唤醒 | 挂钟与单调时钟差 > 30 秒 | L0 | 记 `system.wake`；所有超时 / 无进展计时扣除睡眠时长；强制全部探测跑一轮；唤醒后 60 秒内的失败按上下文归因 | 探测全过即正常 | 不升级 |
| A8 | 网络整体断开 | 网关与题源探测同时失败，且本机默认路由 / DNS 探测失败 | L2 | 两个守护各自挂起；状态句合并显示为「网络不可用」 | 任一探测成功后各自解除 | 60 分钟 |
| A9 | 后端进程崩溃 | launchd 拉起；`starts.json` 上一条 `clean_exit=false` | L0 | 启动宽限期内完成对账与认领（设计 §5.2），沿用运行意图 | 10 秒内恢复调度 | 不升级；转 A11 判断 |
| A10 | 后端卡死（循环不转） | 看门狗 `loop_stalled` 持续 > 300 秒，或独立线程发现事件循环 120 秒无心跳 | L0 | 记栈 → 落盘 → `os._exit(70)` → launchd 拉起 → 同 A9 | 同 A9 | 不升级；转 A11 判断 |
| A11 | 崩溃循环 | 15 分钟内异常退出 ≥ 2 次 | L4 | 本次启动登记 `crash_loop` 全局挂起；不启动任何新阶段；已在跑的容器不动 | 人工解除 | 立即，附最近两次的最后日志 |
| A12 | 机器重启 / 断电 | 启动时容器全无、技能进程全无 | L0 | 所有 `running` 的尝试走「死 × 无」分支：`collect` 失败 → `run.interrupted` 不计次数重新排队；Docker 未就绪时按 A1 等待 | Docker 就绪后自动继续 | 不升级 |
| A13 | 第二个实例被启动 | 实例锁被占 | L0 | 第二个实例退出码 2，提示占用者 pid；不触碰任何状态 | — | 不升级 |
| A14 | 系统时间被改 / 时区变化 | 挂钟回拨（增量为负） | L0 | 记 `system.clock_jump`；以单调时钟为准继续；落盘时间戳照写挂钟 | — | 不升级 |
| A15 | SQLite 被锁或写失败 | `database is locked` / `OperationalError` | L0→L3 | 单次操作重试 3 次（50 / 200 / 800 ms）；连续失败 30 秒 → 全局挂起并持续重试 | 写成功 → 解除 | 5 分钟 |
| A16 | 状态文件损坏 | JSON 解析失败 | L0 | 读 `.bak`；仍失败则空状态启动并由磁盘事实重建；损坏文件改名保留 | 自动 | 记一条升级事件（不阻塞） |

### B. 网关与模型

| # | 情形 | 信号 | 级 | 处置 | 恢复 | 升级 |
|---|---|---|---|---|---|---|

### C. 容器运行

| C1 | 容器起不来 | 预约超过 `phantom_seconds` 无容器且技能进程已退出；或技能返回启动失败 | L1 | 释放预约；`container.start_failed` 退避重试 | — | 连续 3 题 → 即时探测 Docker，不通过转 A1 |

| C3 | 容器被 OOM 杀掉 | `docker inspect` 的 `OOMKilled` 或退出码 137 | L1 | 该题重试 1 次并拉长退避；该工程进冷却；1 小时内 ≥ 2 次 → 弹性 / 容器数建议下调并告警 | — | 1 小时内 ≥ 3 次 |
| C4 | 容器提前退出 | 容器非零退出，会话结构不完整 | L1 | `container.exited` 退避重试 | — | 隔离后在「需处理」 |
| C5 | 运行超时 | 运行时长 > `run_timeout_seconds × 1.25`（扣除睡眠） | L1 | 守护命中：仅观察 → 标记；自动处置 → 技能 `cleanup`，`run.timeout` | — | 隔离 |
| C6 | 运行无进展 | 持有名额期间 30 分钟内所有进展信号都没写入 | L1 | 同 C5，类别 `run.no_progress` | — | 隔离 |
| C7 | 运行结束但会话不完整 | 1–8 步门禁未过 | L1 | `run.incomplete`，最多重试 2 次 | — | 隔离，建议换题；工程进冷却 |
| C8 | 僵尸容器 | 任务在平台与 `state.json` 中**都**是终态，容器仍在运行超过 5 分钟 | L0 | 守护：技能 `cleanup` | — | 不升级 |
| C9 | 孤儿容器 | 带 `solo2611` 标签、不属于任何已知任务、存活 > 30 分钟 | L0 | 计入占用（防超发）；守护列出；自动处置模式下清理 | — | 仅观察模式下进「兜底策略」面板 |
| C10 | 技能进程死了但容器还活着 | 认领表：进程死 × 容器活 | L0 | 保留占用；容器结束后 `collect --container` 收尾 | 收尾成功即正常进入下一阶段 | `collect` 失败 → `run.interrupted` 重新排队 |
| C11 | 后端重启时运行正在进行 | 认领表：进程活 × 容器活 | L0 | 认领并跟随日志，不重启不计次数 | — | — |
| C12 | `state.json` 停在 `running`，现场全无 | 认领表：进程死 × 容器无 | L0 | 技能 `collect`；失败 → `run.interrupted`，不计次数重新排队 | — | 总尝试用尽才隔离 |
| C13 | 用户绕过平台手动跑了 `run` | 容器属于已知任务但不是平台启动的 | L0 | 计入占用；该题标「外部运行中」，平台不重复启动；结束后按磁盘事实续跑 | — | — |
| C14 | 上限被外部改动 | 技能配置的 `maxContainers` ≠ 平台写入值 | L0 | 写回并回读；记 `limit.drift`；暂停启动 20 秒 | 自动 | 1 小时内 ≥ 3 次（有别的东西在改） |

### D. Agent 与桌面会话

技能状态 `run_failed` 表示技能自身的重试预算已经用尽，必须映射为 `blocked`，不能再被外层调度当成 `ready` 自动拉起。

| # | 情形 | 信号 | 级 | 处置 | 恢复 | 升级 |
|---|---|---|---|---|---|---|
| D1 | Agent 可执行文件不存在（CLI） | 启动抛 `FileNotFoundError` / 预检项失败 | L2 | `session_guard` 挂起 sessions；题不标失败 | 每 2 分钟探测；可执行即解除 | 30 分钟 |
| D2 | ChatGPT 桌面端没开 / 崩了 | 进程不存在或深链接调用失败 | L2 | 先尝试 `open -a` 拉起一次并等 20 秒；仍不行 → `session_guard` | 同上 | 30 分钟 |
| D3 | 深链接发出了但会话没建立 | 发出后 N 分钟（默认 5）内按 marker + cwd 找不到 rollout | L1 | `agent.launch_lost`：不计入题目次数，间隔 ≥ 20 秒后重发，最多 2 次 | — | 连续 3 题 → `session_guard` |
| D4 | CodexQueuePush 辅助功能权限丢失 | helper 返回权限错误 | L4 | `session_guard`（`auto=false`） | 人工授权后解除 | 立即 |
| D5 | ChatGPT 未登录 / 会话被登出 | rollout 或 helper 输出命中登录特征 | L4 | 同 D4 | 人工 | 立即 |
| D6 | ChatGPT 用量受限 | 会话终止文本命中用量限制特征 | L2 | `session_guard` 挂起 sessions；能解析出重置时间则到点探测，否则每 15 分钟；容器池不受影响（已起草的题照常运行） | 自动 | 重置时间后 30 分钟仍不行 |
| D7 | 回合被中止 / 流错误 | `turn_aborted` / `stream_error` | L1 | `agent.aborted` 退避重试 | — | 隔离 |
| D8 | Agent 阶段超时 | 超过阶段预算（扣除睡眠） | L1 | 终止 Agent（CLI）或标记会话需手动停止（桌面）；`agent.timeout` 重试 | — | 隔离 |
| D9 | Agent 无进展 | 阶段内 30 分钟所有进展信号无写入 | L1 | 同 D8，类别 `agent.no_progress` | — | 隔离 |
| D10 | Agent 自报可恢复失败 | `AUTOPILOT: FAILED <原因>` | L1 | `agent.reported`；原因与上次相同则止损 | — | 隔离，原因原文可见 |
| D10a | Agent 按规则确认阻断 | `AUTOPILOT: BLOCKED <原因>` | L1 | `agent.blocked`；不消耗重试次数，立即人工隔离 | — | 原因原文可见 |
| D11 | 门禁反复不过 | 技能门禁返回 errors | L1 | `gate.rejected`；errors 指纹与上次相同 → 立即隔离不再重试 | — | 隔离，errors 原文可见 |
| D12 | 回合结束了但门禁没稳定 | `task_complete` 后磁盘门禁仍未全过 | L0 | 等一个稳定窗口（默认 60 秒）再判定，避免把「文件还在落盘」判成失败 | — | — |
| D13 | 提示词模板自检失败 | 模板包含绕过门禁类字样（v2 自检） | L4 | `skill_guard` 挂起 sessions | 人工修模板 | 立即 |
| D14 | 后端重启时 Agent 在跑（CLI） | 启动时发现记录的 Agent 进程仍在且日志在增长 | L0 | 认领并重新跟随日志；否则终止并回到磁盘事实推导（不计次数） | — | — |

## 5. 需要人的最小集合

以下情形没有可靠的自动恢复信号，v3 明确**不**尝试自动恢复，只负责第一时间停下来、说清楚、叫人：

|---|---|---|
| 修复网关 Key / 充值额度 / 纠正模型配置 | B6 B7 B8 | 去设置 → 测试 → 解除挂起 |
| 修复 GitHub Token | F6 | 同上 |
| 授予屏幕录制 / 辅助功能权限 | F1 D4 | 打开系统设置对应面板 |
| 登录 ChatGPT 桌面端 | D5 | 打开 ChatGPT |

| 处理隔离题（重试 / 作废 / 转人工） | 各 L1 用尽后 | 需处理分组 |
| 抽检 | — | 抽检页 |
| 确认崩溃循环 / 未知失败扎堆的原因 | A11 G11 E6 升级后 | 下载诊断包 → 解除挂起 |

其余 70 余种情形，目标是全程不需要人。

## 6. 未知异常的统一兜底

1. 任何循环里的未捕获异常：记录栈 → 本轮结束 → 下一轮照常；同一异常连续 10 轮 → 该循环标 `stalled` 交给看门狗。
2. 任何阶段执行器里的未捕获异常：该阶段按 `unknown.<stage>` 失败处理，绝不让一道题的异常波及其它题。
3. 任何探测器自身抛异常：视为「探测失败」而非「探测通过」。
4. 任何守护自身抛异常：本轮跳过该守护，不执行任何处置。
5. 任何自动处置动作失败（例如 `cleanup` 报错）：记事件、3 次后升级，不无限重试。
6. `unknown` 扎堆（E6 / G11 / FR-RTY-08）→ 停止领取并叫人，避免在未知问题上持续消耗工程与额度。
