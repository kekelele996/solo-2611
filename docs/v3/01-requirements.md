### 1.2 三个循环、三份状态、三种暂停

| 循环 | 周期 | 状态存放 | 暂停语义 |
|---|---|---|---|
| `RunScheduler._tick_loop` | 2 s | **纯内存**（`self.queue` / `self.active`），重启即丢 | 没有暂停 |
| `Autopilot._loop` | — | `autopilot` 状态 JSON（全部 `Job`） | `paused` 布尔 + `breaker.tripped` |
| `IntakeService._loop` | — | 生产计划 JSON | `plan.status = paused` + `pause_reason` 文本 |

后果：运行队列重启后要靠 `Autopilot._advance` 重新入队来「碰巧」恢复；计划暂停、自动交付暂停、熔断三者的组合状态
界面上各显示各的，「现在为什么没在跑」需要人自己拼。

### 1.3 准入判断过于简单，且有一处会超发

`RunScheduler._tick`（`scheduler.py:250`）：

```
used = max(len(docker 容器), len(self.active))；used >= limit 或队列空就返回；否则弹出队首启动
```

- `_running_containers()` 在 `docker ps` 失败时返回**空集合**（`scheduler.py:496`），于是 Docker 响应慢或瞬时报错的那一拍，
  占用数退化为 `len(self.active)`。重启后 `self.active` 为空而容器仍在跑时，这一拍会直接超发。
- 每 2 秒都调一次技能 `config show` 来读上限（`refresh_limit`），等于每天多起 4 万多个子进程。
- 没有启动间隔、没有磁盘门禁（磁盘只在领取时检查，`intake.py` 的 `disk_floor_gb`）、没有启动宽限期。
- `attempt_total` 在三处写死为 3（`scheduler.py:181/192/200`），与设置里的 `execution.attempts` 无关。
- 槽位文件的 `pid` 恒为 `None`（`_write_slot`），重启后无法认领仍在跑的技能进程——
  而技能进程是以 `start_new_session=True` 起的（`gateway/skill.py:162`），后端重启时它**不会**跟着死。

### 1.4 异常处置只有「熔断等人」

| 情形 | 现在的行为 | 代码 |
|---|---|---|
| 任一题失败类别为 `auth` 或 `environment` | 立即全局熔断，必须人工点恢复 | `breaker.py:53` |
| 同类失败连续 3 题 | 同上 | `breaker.py:54` |
| 题源会话过期 | 计划置 `paused`，等人重登再点继续 | `intake.py` `SourceAuthError` 分支 |
| 当前筛选下没有候选 | 计划置 `paused` | `intake.py` `candidate is None` 分支 |
| 磁盘低于阈值 | 计划置 `paused`，磁盘恢复后**不会**自动继续 | `intake.py` 磁盘分支 |
| 后端重启时 Agent 在跑 | 直接 `SIGKILL` 旧 Agent 进程组，任务回 `pending` | `autopilot.py` `_load` |
| `state.json` 停在 `running` 但没有运行实例 | 判失败：「请在任务页处理后重试」 | `autopilot.py` `_advance` |

没有的东西：自动恢复探测、失败退避重试、单题隔离、无进展守护（CLI 模式只有阶段超时）、孤儿 / 僵尸容器回收、
429 感知、后台循环看门狗、崩溃循环识别、睡眠唤醒处理、吞吐统计。

## 2. 目标

1. **调度在现场。** 打开「调度」页就能看到队列、看到上限、改上限、开关队列；常用操作不需要进设置页。
2. **高度自动化。** 一次下达后可以离开机器一整晚：可恢复的故障自己恢复，不可恢复的只影响尽可能小的范围，
   回来时只需要处理「真的需要人」的那几件事。
3. **异常有清单。** 每一种已知异常都有明确的检测信号与处置；未知异常有统一的保守兜底，而不是崩或者死等。
4. **永不超发、永不重复副作用。** 任何时刻容器数不超过上限；领取、建仓、导出、提交不因重启或重试而发生两次。
5. **看得懂。** 任何时刻都能回答：现在跑了几个、还能跑几个、下一个什么时候启动、为什么不启动、过去 24 小时产出多少。

## 3. 非目标

| 不做 | 原因 |
|---|---|
| 多机分布式调度、多用户 | 仍是单机单用户；容器名额只在本机生效 |
| 平台自己起容器或替技能做限流 | 容器链路属于技能；平台只决定「什么时候调用 `run`」 |
| 自动放宽质量门禁来提高通过率 | 硬规矩 10 |
| 自动处理抽检结论 | 抽检永远是人做 |
| 自动重装 / 升级技能、自动修改 Key | 涉及凭据与外部状态，只告警 |
| 参考项目的 A / B 双候选、配额预扣回补 | 2611 是单轮单模型、工程台是领取模型，形态不同 |
| 新增第三方依赖、图表库 | 沿用 v1 / v2 约束 |

`GRD` 守护、`RCV` 重启恢复、`RFL` 补位、`OBS` 可观测。优先级 P0 / P1 / P2。

### 5.4 失败分类与重试（RTY）

| 编号 | 需求 | 级别 |
|---|---|---|
| FR-RTY-01 | 失败类别扩为两级：`family.kind`（如 `gateway.rate_limited`、`container.oom`），每个类别带 是否瞬时、影响范围、是否计入重试次数、退避策略、用尽后的去向 | P0 |
| FR-RTY-02 | 分类优先级：技能结构化输出 / 退出码 → 运行证据（容器退出码、轨迹末条事件）→ 可维护的特征表 → `unknown`；特征表是数据文件，新增一种失败不需要改代码 | P0 |
| FR-RTY-03 | 瞬时失败自动退避重试（默认 1 → 3 → 10 分钟，带 ±20% 抖动），退避期间该题不占任何名额；界面显示「x 分钟后第 n 次重试」 | P0 |
| FR-RTY-04 | 「归因于平台 / 基础设施」的失败不消耗该题的重试次数，但受单题总尝试上限约束，防止无限循环 | P0 |
| FR-RTY-05 | 重复同一错误提前止损：同一题连续两次门禁返回**相同** errors，不再重试，直接转人工 | P0 |
| FR-RTY-06 | 单题隔离：一道题用尽重试后进入「已隔离」，不影响其它题；计划自动补位一道新题（受领取上限约束） | P0 |
| FR-RTY-07 | 同一工程多次失败后进入冷却名单，补位时跳过；失败原因在题源页可见 | P1 |
| FR-RTY-08 | `unknown` 类：重试 1 次；仍失败则隔离该题；滑动窗口内 `unknown` 超过阈值（默认 10 题中 4 题）挂起领取并通知 | P0 |
| FR-RTY-09 | 重试策略表在调度页可见、可调（每类的最大次数与退避）；默认值即可用 | P1 |

### 5.5 守护（GRD）

| 编号 | 需求 | 级别 |
|---|---|---|
| FR-GRD-01 | 守护模式三档：关闭 / **仅观察**（默认，只标记和记日志）/ 自动处置；模式与阈值在调度页就地修改 | P0 |
| FR-GRD-02 | 运行阶段超时：容器运行超过上限（默认 = `run_timeout_seconds` × 1.25）仍未结束 | P0 |
| FR-GRD-03 | 无进展：任务持有名额期间，`state.json`、`monitor/`、轨迹、workspace（跳过依赖目录）、Agent 日志在阈值内（默认 30 分钟）都没有写入 | P0 |
| FR-GRD-04 | 阶段预算：起草 / 交付 / 录屏 / 导出各有时长预算，超出即按 FR-RTY 处理；取代「ChatGPT 12 小时无进展」这一个粗阈值 | P0 |
| FR-GRD-05 | 僵尸容器：任务已终态（平台记录与 `state.json` **同时**为终态）但容器仍在跑 → 走技能 `cleanup` | P0 |
| FR-GRD-06 | 孤儿容器：带 `solo2611` 标签、不属于任何已知任务、存活超过阈值 → 仅观察模式下列出，自动处置模式下清理 | P0 |
| FR-GRD-07 | 残留进程：任务结束超过阈值后其目录下仍有进程（排除登录 shell 与平台自身）→ `SIGTERM` | P1 |
| FR-GRD-08 | 领取泄漏：已领取但超过阈值没有对应任务、或任务已作废 / 隔离 → 归还 | P0 |
| FR-GRD-09 | 尝试次数膨胀：任一计数器异常增长（≥ 50）→ 停止累加、隔离该题并告警 | P0 |
| FR-GRD-10 | 守护的每次命中列在调度页「兜底策略」面板：命中项、依据、已做 / 将做的动作；仅观察模式下每项可一键手动执行 | P0 |
| FR-GRD-11 | 守护从不处理：登录 shell、平台自身进程、用户显式标记「保留」的任务、不属于本平台任务目录的任何东西 | P0 |

### 5.6 重启恢复与看门狗（RCV）

| 编号 | 需求 | 级别 |
|---|---|---|
| FR-RCV-01 | 运行队列、退避计时、挂起、弹性状态全部落盘；重启后 10 秒内恢复且不重复启动任何阶段 | P0 |
| FR-RCV-02 | 认领存活的运行：重启时对每个记录在案的运行，按「技能进程是否存活 × 容器是否存活」四种组合分别处理（设计 §5.2），不再一律判失败或杀掉 | P0 |
| FR-RCV-03 | 启动宽限期：重启后先完成一次对账与认领，再开始启动新任务（默认至少 20 秒） | P0 |
| FR-RCV-04 | 副作用意图日志：领取、建仓 / 首次推送、导出、提交在执行前写意图、执行后写结果；重启后对未决意图按外部事实收敛，保证不重复 | P0 |
| FR-RCV-05 | 后台循环心跳：每个循环每轮上报；超过阈值没完成一轮记 `watchdog.loop_stalled`（附该任务当前挂起的调用点）；循环意外退出自动拉起 | P0 |
| FR-RCV-06 | `/api/health` 的 `ok` 反映循环健康；循环持续卡死超过上限时进程自行退出，由 launchd 拉起 | P0 |
| FR-RCV-07 | 崩溃循环：15 分钟内异常退出 ≥ 2 次，本次启动自动进入挂起并通知；否则沿用上次的运行意图（上次是运行就继续运行） | P0 |
| FR-RCV-08 | 睡眠唤醒：检测到挂钟与单调时钟的跳变后，所有「无进展 / 超时」计时扣除睡眠时长，并立即重跑全部探测 | P0 |
| FR-RCV-09 | 调度运行期间阻止系统空闲睡眠（`caffeinate -i`），暂停或排空完成后释放；可在调度页关闭 | P1 |
| FR-RCV-10 | 状态文件损坏容错：任何 JSON 状态文件读失败时回退到上一份备份或由磁盘事实重建，绝不因此拒绝启动 | P0 |

## 6. 非功能需求

| 编号 | 类别 | 要求 |
|---|---|---|
| NFR-V3-01 | 安全上限 | 任何情况下（含重启、Docker 抖动、并发改配置）运行中的受管容器数 ≤ 生效上限；「收敛中」除外且只降不升 |
| NFR-V3-02 | 幂等 | 领取、建仓、导出、提交在任意时刻杀进程重启后都不重复发生；验收用随机杀进程验证 |
| NFR-V3-03 | 自愈时效 | 可恢复故障消失后，调度在 1 个探测周期 + 10 秒内恢复启动 |
| NFR-V3-04 | 响应 | 门禁循环每拍 ≤ 200 ms（不含外部探测，探测全部异步且有超时）；改上限后 ≤ 1 拍生效 |
| NFR-V3-05 | 循环隔离 | 门禁循环不得被任何慢操作阻塞（领取、登录、下载、探测都在别的循环里） |
| NFR-V3-06 | 开销 | 空闲时每分钟外部子进程调用 ≤ 6 次（现状仅读上限一项就是 30 次） |
| NFR-V3-07 | 可回退 | `dispatch.engine = "v2"` 一键回到 v2 调度；数据向后兼容，回退不丢队列 |
| NFR-V3-08 | 可测试 | 所有守护与探测有故障注入点；调度内核可在无 Docker、无技能、虚拟时钟下跑完全部单测 |
| NFR-V3-09 | 可解释 | 任一非运行状态都有结构化原因码 + 中文说明；原因码是稳定枚举 |
| NFR-V3-10 | 审慎 | 破坏性自动动作默认关闭（仅观察）；开启后每次动作都有事件、有依据、可在日志里复盘 |

## 7. 成功判据

- 下达「持续生产，每日上限 30」后离开 12 小时，期间人为制造 网关断 20 分钟、Docker 重启一次、后端被杀两次、
  题源会话过期一次：**无需任何人工操作**，全部自行恢复，容器从未超过上限，没有重复领取 / 重复导出。
- 健康时段容器利用率（运行容器·时间 ÷ 上限·时间）≥ 85%（有足够候选的前提下）。
- 回到机器时，「需处理」里只有真正需要人的条目（抽检、鉴权、隔离题），每条都有明确的下一步。
- 调整并发的全过程在调度页完成，≤ 2 次点击，≤ 2 秒生效。
- 任何「没在跑」的时刻，页头状态句给出的原因与实际一致（验收逐项核对）。
